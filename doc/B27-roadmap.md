# B27 多用户产品化演进路线（2026-10-28 起）

> 背景：B26 第一期（网页端多用户 + 个人数据挂 uid）实施中。用户在本日提出产品化方向建议，
> 本文档先记录建议原文要点与冲突分析，调研结论与执行路线待补充定稿。

## 1. 用户建议原始记录（2026-10-28）

1. **好友绑定邮箱**：admin 发邀请码后，好友可绑定/使用邮箱登录，避免忘记随机口令。
2. **登录系统复用开源方案**：网上找成熟实现直接用，不自己造轮子。
3. **更丰富的个人配置**：想看 Skill 与看几条、想看论文与论文方向都由用户自选——
   不限于 AI+具身智能，可以是 AI+其他领域，甚至非 AI（例：法律方向用户）也能用同一套逻辑。
4. **更多个性化**：人多之后允许用户配置自己的 API 地址/Key 等。
5. **产品化**：向「成品的多用户个性化日报推送系统」演进，不要太 Demo，要更商业化。
6. **调研开源类似方案**：学习它们的架构、用户管理、内容层与用户层如何分离。
7. **模块化**：所有板块/功能可插拔地加入和删除；用户可以在仓库里添加自己的模块，
   底座只需要对应好模块接口。

## 2. 冲突分析：以上建议 vs 进行中的 B4/P1

**结论：不冲突，B4/P1 继续做完（已获用户授权：不冲突则完成后再汇报）。**

| 建议 | 影响层 | 与 B4/P1 的关系 |
|---|---|---|
| 邮箱绑定/登录 | 认证层 | 纯增量：users 表加 email 列 + 登录逻辑扩展；P0 已建的表结构不动 |
| 复用开源登录库 | 认证层实现 | 不动数据层；B4/P1 的 uid 挂载与认证实现解耦（uid 来自 users 表主键） |
| 论文方向自选（非 AI 用户） | L1 内容池（频道化演进） | B4/P1 的个人偏好层是「订阅频道」的前提，方向一致 |
| 自配 API 地址/Key | user_settings | 该表本就是通用 KV（user_id, key, value），直接可存 |
| 模块化插件 | 板块层组织方式 | 与数据层正交；个人配置读取接口（user_settings/user_keywords）不变 |

## 3. 开源调研结论（2026-10-28 定稿）

### 3.1 认证方案选型（对应建议 ①②：邮箱登录、复用开源）

| 方案 | 结论 | 理由 |
|---|---|---|
| **pwdlib[argon2]**（密码哈希） | ✅ 采用 | FastAPI 官方文档现推荐的 passlib 继任者；活跃维护、API 简洁 |
| **itsdangerous**（签名 token） | ✅ 采用 | Flask 同款久经考验；URLSafeSerializer 生成魔法链接 token（max_age≈15 分钟），也可做签名 cookie |
| 标准库 smtplib | ✅ 采用 | 复用现有 alert_mail 发信链路与 EMAIL_PASSWORD，不引入第三方邮件 SDK |
| fastapi-users | ❌ 不采用 | 已进维护模式；强绑 SQLAlchemy 全家桶，与本项目裸 sqlite3 + 挂 uid 模式冲突 |
| passlib | ❌ 不采用 | 2020 年起停维护，Python 3.13+ 兼容性已损坏 |
| 自研哈希/签名 | ❌ 禁止 | 用户明确要求复用成熟实现，安全层绝无自造轮子 |

**登录形态（B27-A 定稿）**：邀请码仍是唯一入口（admin 发码）→ 好友首次用邀请码登录 → 绑定邮箱（可选设密码）→ 此后邮箱登录：密码（pwdlib argon2 校验）或魔法链接（邮件含 itsdangerous 签名 token，15 分钟有效，点击即登录）。users 表 email 列已在 B26 P0 就位。

### 3.2 架构印证（对应建议 ⑤⑥：产品化方向）

对标 newsnow（~21k star）与 Folo（~38k star，130 万订阅源）：
- 均为「**全局内容池 + 用户层**」结构——采集/清洗/去重/打分一次成本全局复用；用户只挂订阅、偏好、已读、个人视图；
- 与 B26 落成的三层模型（L1 全局内容池 → L2 用户层挂 uid → L3 分发层按人渲染）**完全同构**，方向无需调整；
- 差距在：订阅频道由用户自选（newsnow 的频道即分类 Tab）、账号体系（邮箱/OAuth）、个性化分发——分别对应 B27-B、B27-A、B26 第二期 P3。

### 3.3 模块化插件模式（对应建议 ⑦）

采用 **manifest 文件夹式**（Home Assistant integrations 同款）：
- 每个板块一个目录：`manifest.json`（声明名称/依赖/提供的数据表与接口/前端入口）+ 板块代码；
- 底座启动时扫描目录、校验 manifest、动态 import 注册——**用户加模块 = 在仓库里加一个目录并实现约定接口**，底座只认接口不认具体模块；
- 备选否决：pluggy 偏重（hook 机制对「板块级插拔」过度设计）；entry_points 不适合「用户在仓库里加文件夹」的场景。

## 4. 执行路线（B27 四阶段，每阶段独立上线、可回退）

| 阶段 | 内容 | 依赖 | 上线判据 |
|---|---|---|---|
| **A 邮箱登录** | 绑定邮箱（可选密码 pwdlib argon2）；邀请码首登→绑邮箱→此后邮箱+密码或魔法链接（itsdangerous token 15min）登录；发信复用 alert_mail 链路 | B26 P0（已完成） | 好友忘码可自助登录；用户管理页可见绑定状态 |
| **B 方向频道化** | L1 内容池按「频道」组织：论文方向=arXiv 分类集+关键词频道，Skill/热榜/探索各自成频道；用户自选订阅集合，研究兴趣升级为频道订阅；非 AI 领域（如法律）=自定义源+关键词频道，底座逻辑不变 | B26 第一期（已完成） | 法律方向用户可订阅并收到自己方向的日报；AI+具身默认频道不变 |
| **C 个人 API 配置** | user_settings KV 存自配 API 地址/Key；个人触发型调用（解读/分析）优先用本人配置，全局池任务仍走系统 API；⚙ 面板加「我的 API」卡 | B26 P1（已完成） | 用户填自己的 Key 后其触发的解读走该端点，成本可分摊 |
| **D 板块插件化** | 板块目录化 + manifest.json + 底座注册表扫描动态加载；数据表/接口/前端入口全部声明式；用户模块零改动底座 | A/B/C 稳定后 | 新板块只加目录即上线；删目录即下线，底座零修改 |

**执行原则**：
1. 每阶段完成真库验证 + CHANGELOG 条目 + commit，再进下一阶段；
2. 任何阶段与进行中工作冲突即停下汇报、必要时回退（延续本期授权约定）；
3. B26 第二期 P3（个性化邮件分发）可与 B27-B 合并实施（同在分发层动手，避免改两遍）。
